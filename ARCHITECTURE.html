Growth99 platform · the client

One onboarding form, answered in three parts

The form is generated for the won deal and sent to the client. It asks plain questions about the business and its current website — no technical input. Each part does real work the moment it is submitted.

PART 1

The business

  • Practice name, location, phone
  • What the business does and who it serves
  • The current website address
On submit → account and resources are created
PART 2

The website

  • Treatments and services offered
  • Headline, call to action, booking tool
  • Providers, reviews, tone of voice
  • A website they admire, used as the design reference
On submit → the beta site build starts
PART 3

The finishing details

  • Logo, imagery and consent
  • Lead alerts and contact routing
  • Anything still outstanding
Completes the client's record

Website Build Tool · automated

Eight steps turn the answers into a published website

Submitting Part 2 notifies the Website Build Tool, which runs the whole build on its own and reports each step as it goes. Nobody writes code, opens a pull request, or clicks publish.

1

Audit the website they have today

The current site is fetched and scored — design, usability, conversion path, copy, speed and SEO. This becomes the “before” benchmark the new site is measured against.

Existing site from HubSpotBefore score
2

Learn the brand, then write the build brief

Colours, typography and visual tone are read off the existing site and combined with the form answers. Gemini turns all of it into a detailed brief describing the site to be built.

Google GeminiBrand colours · fonts · tone
3

Generate the pages

Stitch designs the home, treatments, about and contact pages from that brief — grounded in the client's real content and the reference site they admire.

Stitch4 pages as HTML
4

Assemble one coherent website

The separate pages are joined into a single site with shared navigation and footer, then converted by Gemini into a working WordPress theme.

Google GeminiWordPress theme
5

Commit the code and open a pull request

The theme is pushed to the GitHub repository recorded on the deal, and a pull request is opened so every change is reviewable and reversible.

GitHubRepo from the deal property
6

Wait for the checks, then merge

Automated tests run against the new code. The pull request merges only when they all pass — and if a check fails, the tool attempts a fix and tries again.

Continuous integrationMerged on green
Checks failing → the build stops here, nothing goes live
7

Publish and activate the theme

The merged code deploys to the beta address from the deal, the new theme is activated, and the site's pages and navigation are created automatically.

WordPressSite is live
8

Audit again and compare

The live site is scored with the same measures as step 1, producing a plain before-and-after report of what the rebuild actually improved.

Before → after report

Automated · runs on its own after launch

Then it adds a page for every treatment

Once the beta site is live, a second job starts by itself. It gives each treatment its own proper page — the depth a real practice website needs — and publishes a brand guide alongside them.

1

Study how the admired site presents a treatment

The reference website from the form is scanned to learn how its treatment pages are structured — section order, imagery, and how location is worked into headings.

Reference site structure
2

Take the treatments from the form, revenue first

The services the client listed become the page list — highest-value treatments first, up to ten pages. Their existing pages supply the real facts to rewrite.

Up to 10 treatmentsCopy grounded in their site
3

Write a brief per treatment, then design each page

Gemini writes a bespoke brief for every treatment, and Stitch designs the page from it — so all the pages share one look while each reads as its own.

Google GeminiStitch
4

Publish them the same reviewable way

All the new pages ship in a single pull request, pass the same checks, merge, and appear in the site's Treatments menu — together with a public brand guide.

Where a person is needed — and where they aren't

The whole value of the pipeline is how short the left-hand column is.

A person does exactly two things

  1. Records the GitHub repository and beta site address on the won deal.
  2. Sends the onboarding form — and the client answers it.

Optional: someone can require sign-off before anything merges, per website.

Everything else is automatic

  • Auditing the current site and scoring it
  • Reading the brand and writing the build brief
  • Designing and assembling every page
  • Committing code, opening and merging pull requests
  • Publishing, activating and re-auditing the site
  • Adding a page per treatment, plus the brand guide
